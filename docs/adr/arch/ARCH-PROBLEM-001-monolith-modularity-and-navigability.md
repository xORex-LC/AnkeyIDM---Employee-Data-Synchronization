# ARCH-PROBLEM-001: Горизонтально-слоёный монолит затрудняет навигацию и не изолирует стадии структурно

> **Статус**: Решена в [ARCH-DEC-001](./ARCH-DEC-001-modular-monolith-uv-workspace.md)
> **Дата создания**: 2026-06-16
> **Затронутые компоненты**: пакет `connector` целиком (`domain/`, `infra/`, `usecases/`, `delivery/`), `pyproject.toml`, dev-toolchain

---

## 📋 Контекст

Приложение — единый дистрибутив `connector`, организованный **горизонтально по слоям**
(`domain/usecases/infra/delivery`). Стадии ETL-конвейера (extract, map, normalize, enrich, match,
resolve, topology) и сквозные концерны (diagnostics, logging, reporting, dsl) «размазаны» по этим
слоям: например, extract — это `domain/transform/core/extractor.py` + `infra/sources/*` +
`domain/ports/transform/*` одновременно.

Проект вырос; число подсистем — два десятка. Появилась потребность развивать и тестировать стадии как
самостоятельные единицы и понимать «что где живёт» без удержания всей карты в голове.

---

## ⚠️ Проблема

Горизонтальная раскладка по слоям при текущем масштабе:

1. **Когнитивная нагрузка / навигация.** Одна стадия физически разбросана по 3–4 каталогам разных слоёв.
   Чтобы понять/изменить стадию, нужно держать в голове всю карту репозитория («теряюсь что где»).
2. **Нет структурной изоляции стадий.** Ничто на уровне сборки не мешает стадии импортнуть соседнюю
   стадию или чужую инфраструктуру. «Агностичность» держится только на дисциплине и общем
   import-linter, а не на физической границе пакета.
3. **Нет независимой единицы разработки/тестирования/версионирования.** Стадия не может быть собрана,
   протестирована или переиспользована отдельно — всё связано в один дистрибутив.
4. **Блокирует будущую эволюцию.** Любой будущий per-stage runtime-split (ось B, RMQ-стиль) невозможен,
   пока стадии не являются отдельными единицами кода.

---

## 🔍 Симптомы

- **Симптом 1**: Чтобы тронуть extract, правки идут в `domain/transform/core/` **и** `infra/sources/`
  **и** `domain/ports/transform/` — три слоя ради одной стадии.
- **Симптом 2**: «Где живёт X?» требует поиска по всему дереву; per-dir README помогают, но карты целиком нет.
- **Симптом 3**: Структурно ничто не запрещает sibling-зависимость между стадиями — только ревью/линтер.

---

## 📊 Масштаб проблемы

- **Частота**: Постоянно при разработке/навигации; растёт с числом стадий и подсистем.
- **Критичность**: Средняя (не ломает рантайм), но прямо тормозит развитие и понимание для maintainer'а.
- **Затронуто**: Весь репозиторий; все будущие изменения стадий/подсистем.

---

## 🧪 Как воспроизвести

1. Поставить задачу «изменить только стадию extract, ничего лишнего не задев».
2. **Ожидаемый результат**: стадия — одна самодостаточная единица с явной границей.
3. **Фактический результат**: правки расходятся по `domain/`, `infra/`, `ports/`; граница только логическая.

---

## 🚫 Почему это проблема?

- Навигация и понимание — главный тормоз для одиночного maintainer'а.
- «Агностичность» стадий не гарантирована структурно (только дисциплиной).
- Нет пути к независимой разработке/тестированию и к будущему per-stage split.

## 💡 Возможные решения (обсуждение)

> Детальный разбор, карта и таксономия — в worknote
> [MODULARIZATION_VISION_WORKNOTE](../../notes/modularization/MODULARIZATION_VISION_WORKNOTE.md).

### Вариант 1: Модульный монолит — package-by-feature на uv workspace
- **Идея**: kernel + сквозные shared-пакеты + пакет на стадию (вертикальный гексагон), правило
  «зависимости только вниз». Один процесс, in-memory транспорт (ось A).
- **Плюсы**: структурная граница и изоляция стадий, навигируемость, путь к будущему split (no-op).
- **Минусы**: ~24 пакета, churn импортов, сложность сборки.

### Вариант 2: Оставить горизонтальные слои, усилить только доками/линтером
- **Идея**: единый пакет + карта + import-linter contracts по стадиям.
- **Плюсы**: ноль изменений сборки.
- **Минусы**: нет физической границы; «размазанность» стадий по слоям сохраняется.
